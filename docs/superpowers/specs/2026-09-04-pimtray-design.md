# PimTray — macOS menu bar app for Microsoft Entra PIM

Date: 2026-09-04
Status: approved design, pending implementation plan

## 1. Purpose

PimTray is a macOS menu bar application that lets a user sign in with one or
more Microsoft Entra identities, see the Privileged Identity Management (PIM)
roles each identity holds in each tenant it has access to, and activate or
deactivate those roles without opening the Entra portal.

Success criteria:

- Sign in with several identities; each identity may span several tenants
  (home tenant plus customer or guest tenants).
- Clicking the status item shows identities, grouped by tenant, with every
  eligible role and its activation state.
- A role can be activated with a duration (defaults to the tenant policy
  default, capped at the policy maximum) and a reason (remembered per role).
- Several roles across identities and tenants can be selected and activated in
  one bulk operation with a shared reason.
- Active roles show a green indicator and a live countdown; they can be
  deactivated early; a notification fires five minutes before expiry.
- When role discovery is blocked by tenant consent policy, the user can
  configure the roles they believe they hold ("Configure known PIM roles...")
  and activation still works.

## 2. Scope and phasing

Three PIM scopes are in scope, delivered in phases behind one provider
abstraction so later phases add a provider without touching the app shell.

| Phase | Provider | API |
|---|---|---|
| 1 | Entra ID directory roles | Microsoft Graph v1.0 `roleManagement/directory/*` |
| 2 | Azure resource roles | Azure Resource Manager `Microsoft.Authorization/*ScheduleRequests` |
| 3 | PIM for Groups | Microsoft Graph v1.0 `identityGovernance/privilegedAccess/group/*` |

Phase 1 is the deliverable of the first implementation plan. Phases 2 and 3
are designed here so their data model and manual-configuration UI are not
retrofitted later, but their providers are stubs until their own plans.

Out of scope: approval workflows beyond showing "pending approval", ticket
number fields unless a policy reports them required, App Store distribution,
Windows or iOS.

## 3. Platform and tooling

- Swift 6 with strict concurrency, SwiftUI, minimum deployment macOS 26.
- Menu bar UI via `MenuBarExtra` with `.window` style. Use standard materials
  and Liquid Glass effects (`glassEffect`) for the panel and sheets where the
  system provides them; no custom chrome.
- State via the Observation framework (`@Observable`), no Combine.
- Authentication via MSAL for iOS and macOS (Swift Package `MSAL`).
- Project layout: a Swift Package `PimTray` with targets `PimTrayCore`
  (library, no UI, no MSAL import), `PimTrayApp` (executable app), and
  `PimTrayCoreTests`. The Xcode project is generated by XcodeGen from
  `project.yml`; the generated `.xcodeproj` is git-ignored.
- Local development signing with a development certificate. MSAL requires a
  signed binary for persistent keychain cache. Keychain group
  `com.microsoft.identity.universalstorage` is declared in entitlements.
- Distribution: personal use, built from Xcode. No notarization step.

## 4. Entra app registration (prerequisite, documented in README)

A single multi-tenant public client registration owned by the user:

- Platform: iOS/macOS with bundle ID `no.frodehus.pimtray` (configurable),
  redirect URI `msauth.no.frodehus.pimtray://auth`.
- "Allow public client flows": yes.
- Delegated Graph permissions requested at sign-in (consent may be granted
  per tenant by an admin; absence of consent is the trigger for manual mode):
  - `User.Read`
  - `RoleEligibilitySchedule.Read.Directory`
  - `RoleAssignmentSchedule.ReadWrite.Directory`
  - `RoleManagementPolicy.Read.Directory`
  - Phase 3: `PrivilegedEligibilitySchedule.Read.AzureADGroup`,
    `PrivilegedAssignmentSchedule.ReadWrite.AzureADGroup`
- Phase 2 ARM scope: `https://management.azure.com/user_impersonation`.

Client ID and bundle ID are read from `PimTrayConfig.plist` so the repo does
not hard-code a tenant-specific value.

## 5. Data model (`PimTrayCore`)

```
Identity
  id: String               // MSAL home account identifier
  upn: String
  displayName: String
  homeTenantId: String

TenantContext
  identityId: String
  tenantId: String
  displayName: String
  source: .home | .discovered | .manual
  discoveryMode: .automatic | .manualRoles
  lastDiscoveryError: String?

RoleScope (enum, Codable, Hashable)
  .entraDirectory(roleDefinitionId: String, directoryScopeId: String)
  .azureResource(scope: String, roleDefinitionId: String)
  .group(groupId: String, accessId: .member | .owner)

RolePolicy
  defaultDuration: Duration      // manual roles: 1 h
  maximumDuration: Duration      // manual roles: 8 h
  requiresJustification: Bool    // manual roles: true
  requiresTicket: Bool           // manual roles: false
  requiresApproval: Bool         // manual roles: false

EligibleRole
  key: RoleKey                    // identityId + tenantId + RoleScope
  displayName: String
  source: .discovered | .manual
  policy: RolePolicy

ActiveAssignment
  roleKey: RoleKey
  assignmentId: String?           // provider-specific id, nil while pending
  startDateTime: Date
  endDateTime: Date?
  status: .active | .pendingApproval | .pendingProvisioning | .failed(String)

ActivationRequest
  roleKey: RoleKey
  duration: Duration
  justification: String
  ticket: (number: String, system: String)?
```

The same role definition can exist in several tenants; `RoleKey` includes
`tenantId`, so those are distinct rows everywhere.

Persistence (JSON under `~/Library/Application Support/PimTray/`):

- `state.json`: identities, tenant contexts, manual roles per tenant,
  remembered justification per `RoleKey`, last-used duration per `RoleKey`.
- Tokens are never stored by PimTray; they live in MSAL's keychain cache.
- Active assignments and discovered roles are an in-memory cache refreshed
  on panel open and on a 60 s background timer while any role is active.

## 6. Authentication

`TokenProviding` protocol in Core:

```
protocol TokenProviding {
  func signIn() async throws -> Identity
  func signOut(_ identity: Identity) async throws
  func accessToken(identity: Identity, tenantId: String,
                   scopes: [String], claims: String?) async throws -> String
  func identities() async throws -> [Identity]
}
```

`MSALTokenProvider` in the App target implements it:

- One `MSALPublicClientApplication` with a multi-tenant (`organizations`)
  authority for sign-in.
- Per call, `acquireTokenSilent` with an authority of
  `https://login.microsoftonline.com/{tenantId}` for the same `MSALAccount`,
  so tokens are issued by the correct tenant.
- On `MSALErrorInteractionRequired`, or when a caller passes `claims`, it
  runs `acquireToken` interactively with `claimsRequest`, presenting the
  system web view anchored to the panel window.
- Sign-in uses the system browser (`ASWebAuthenticationSession` via MSAL's
  default `webviewType`) with the `msauth.<bundleId>://auth` redirect. The app
  forwards the URL open event to `MSALPublicClientApplication.handleMSALResponse`.

Claims challenge handling (mandatory: Graph documents that self-activation
must occur in an MFA-challenged session). A 401 with `WWW-Authenticate:
Bearer ... claims="<base64>"` is decoded by `ClaimsChallenge.parse`; the
coordinator retries the failed call once with the claims passed to the token
provider. Bulk activation pauses per identity+tenant while the prompt is up,
then resumes.

Tenant discovery after sign-in:

1. Acquire an ARM token in the home tenant and call
   `GET https://management.azure.com/tenants?api-version=2022-12-01`.
2. Present the list; the user ticks which tenants to track. The home tenant
   is always tracked.
3. "Add tenant..." accepts a tenant ID or a verified domain. A domain is
   resolved through `https://login.microsoftonline.com/{domain}/v2.0/.well-known/openid-configuration`
   and the `issuer` claim's GUID is stored.
4. If the ARM call fails (no Azure access, consent denied), step 1 is
   skipped silently and only step 3 is available.

## 7. Providers

```
protocol PIMProvider: Sendable {
  var kind: RoleScopeKind { get }
  func eligibleRoles(identity: Identity, tenant: TenantContext) async throws -> [EligibleRole]
  func activeAssignments(identity: Identity, tenant: TenantContext) async throws -> [ActiveAssignment]
  func policy(for role: EligibleRole) async throws -> RolePolicy
  func activate(_ request: ActivationRequest, identity: Identity) async throws -> ActiveAssignment
  func deactivate(_ assignment: ActiveAssignment, identity: Identity) async throws
}
```

Every provider receives an `HTTPClient` (thin `URLSession` wrapper injected
for tests) and the `TokenProviding` instance. Errors are normalised to
`PIMError`:
`.consentRequired`, `.claimsChallenge(String)`, `.notEligible`,
`.policyViolation(String)`, `.pendingApproval`, `.network(Error)`,
`.unexpected(status: Int, body: String)`.

### 7.1 EntraDirectoryProvider (phase 1)

- Eligible: `GET /roleManagement/directory/roleEligibilitySchedules/filterByCurrentUser(on='principal')?$expand=roleDefinition`
- Active: `GET /roleManagement/directory/roleAssignmentScheduleInstances/filterByCurrentUser(on='principal')?$expand=roleDefinition`
  filtered to `assignmentType == 'Activated'`; pending requests from
  `roleAssignmentScheduleRequests/filterByCurrentUser(on='principal')` with
  status `PendingApproval` are merged in.
- Policy: `GET /policies/roleManagementPolicyAssignments?$filter=scopeId eq '/' and scopeType eq 'DirectoryRole' and roleDefinitionId eq '{id}'&$expand=policy($expand=rules)`.
  Reads `unifiedRoleManagementPolicyExpirationRule` (`Expiration_EndUser_Assignment`)
  for max duration and `unifiedRoleManagementPolicyEnablementRule`
  (`Enablement_EndUser_Assignment`) for justification, MFA, ticket flags.
  Default duration equals the policy maximum, matching the portal; the
  last duration the user chose for that role overrides it.
- Activate: `POST /roleManagement/directory/roleAssignmentScheduleRequests`
  with `action: selfActivate`, `principalId` (from `/me`), `roleDefinitionId`,
  `directoryScopeId`, `justification`, `scheduleInfo.expiration
  {type: afterDuration, duration: PT{n}M}`, optional `ticketInfo`.
- Deactivate: same endpoint with `action: selfDeactivate`.
- A 403 on the eligible call raises `.consentRequired`; the coordinator
  flips that tenant to `discoveryMode = .manualRoles`.

### 7.2 AzureResourceProvider (phase 2, stub in phase 1)

- Token scope `https://management.azure.com/user_impersonation`.
- Eligible: `GET https://management.azure.com/providers/Microsoft.Authorization/roleEligibilityScheduleInstances?api-version=2020-10-01&$filter=asTarget()`.
- Active: `roleAssignmentScheduleInstances?...&$filter=asTarget()`.
- Activate: `PUT {scope}/providers/Microsoft.Authorization/roleAssignmentScheduleRequests/{newGuid}?api-version=2020-10-01`
  with `requestType: SelfActivate`; deactivate with `SelfDeactivate`.
- Policy: `roleManagementPolicyAssignments` at scope.

### 7.3 GroupProvider (phase 3, stub in phase 1)

- Eligible: `GET /identityGovernance/privilegedAccess/group/eligibilitySchedules/filterByCurrentUser(on='principal')?$expand=group`.
- Active: `.../assignmentScheduleInstances/filterByCurrentUser(on='principal')`.
- Activate: `POST /identityGovernance/privilegedAccess/group/assignmentScheduleRequests`
  with `action: selfActivate`, `accessId`, `groupId`, `principalId`,
  `scheduleInfo`, `justification`.

### 7.4 Manual role source

`ManualRoleSource` is not a provider. For a tenant in `manualRoles` mode it
produces `EligibleRole` values with `source: .manual` and the default manual
`RolePolicy`, and the matching provider (by `RoleScope` kind) is still used
for activate/deactivate. After a successful activation the policy for that
role is fetched opportunistically and cached if the call succeeds.

Built-in Entra role catalogue: `EntraBuiltInRoles.json` resource in Core,
generated from the Microsoft Learn "Microsoft Entra built-in roles"
reference page (role name, template ID, one-line description). A script
`Scripts/update-role-catalogue.swift` regenerates it. Phase 1 ships the
catalogue as of 2026-09.

## 8. Activation coordinator

`ActivationCoordinator` (Core, `@Observable`, main-actor state, background
work in structured tasks):

1. Receives `[ActivationRequest]` (one for single, many for bulk).
2. Groups by identity and tenant, resolves the provider by scope kind.
3. Per group, runs requests sequentially (Graph throttles parallel PIM
   writes); groups run concurrently.
4. On `.claimsChallenge`, requests a token with claims and retries that
   request once. On `.consentRequired`, marks the tenant manual and fails
   the request with a user-facing message.
5. Stores `justification` and `duration` per `RoleKey` on success.
6. Refreshes active assignments for the touched tenants and reschedules
   expiry notifications.

Per-request outcome is reported to the UI as
`.activated(endDate)`, `.pendingApproval`, `.failed(message)`.

Countdown: the UI derives remaining time from `endDateTime` and a
one-second `TimelineView`; no timers per row.

## 9. UI

### Menu bar item

- Template icon (shield). Badge count of active roles across everything;
  icon tinted when at least one role is active.

### Panel (`MenuBarExtra` window)

```
[PimTray]                           [Select] [Refresh] [⋯]
▼ frode@contoso.com
  ▼ Contoso (home)                              2 active
     ● Global Reader        02:41 remaining     [Deactivate]
     ● User Administrator   02:41 remaining     [Deactivate]
       Exchange Administrator                   [Activate]
  ▼ Fabrikam (manual roles)                     0 active
       Global Administrator                     [Activate]
▼ frode.admin@northwind.com
  ▼ Northwind                                   pending approval 1
     ◐ Privileged Role Admin  awaiting approval [Cancel]
[Add account…]                                  [Quit]
```

- Identity section header: UPN, menu with "Sign out", "Add tenant…",
  "Discover tenants…".
- Tenant section header: display name, active count, "(manual roles)" badge
  when in manual mode, menu with "Configure known PIM roles…",
  "Retry discovery", "Remove tenant".
- Role row: name, state glyph (green dot active, half dot pending, none
  eligible), countdown, primary button. Phase 2 and 3 rows show a subtle
  scope line (subscription name / group name) under the role name.
- Select mode: checkboxes appear on every eligible row; a sticky footer
  button "Activate N roles" opens the bulk sheet. Esc leaves select mode.

### Activation sheet (single)

Reason text field pre-filled from the remembered justification for that
role. Duration picker in 30-minute steps from 30 min to policy max,
pre-selected to last-used or policy default. Ticket fields appear only when
`requiresTicket`. Activate button disabled until reason is non-empty when
required.

### Bulk activation sheet

One shared reason field (pre-filled from the most recently used justification
among the selected roles). A table grouped by identity and tenant with a
duration column per role, pre-filled per role as in the single sheet.
Progress column updates live as requests complete; failures show inline
with a Retry button per row.

### Configure known PIM roles… (per tenant)

Window with three tabs matching the scope kinds:

- Entra roles: searchable multi-select list from the built-in catalogue.
- Azure resources: table of (scope, role name) free-form rows with a
  role-name picker from the built-in Azure roles subset (Owner, Contributor,
  Reader, User Access Administrator, plus free text).
- Groups: table of (group ID, member/owner).

Saving writes the manual roles for that tenant and refreshes the panel.

### Notifications

`UserNotifications` local notification five minutes before each active
assignment ends, with an "Extend" action that re-opens the activation sheet
for that role. Requires permission prompt on first activation.

## 10. Error handling

| Situation | Behaviour |
|---|---|
| Discovery 403 in a tenant | Tenant flips to manual mode, header shows badge, error text in tenant menu |
| Claims / MFA challenge | Interactive prompt once, retry; on second failure show "MFA required" on the row |
| Policy violation (duration too long, justification missing) | Sheet shows server message, stays open |
| Approval required | Row shows pending state; refresh polls the request status |
| Network offline | Rows keep last state, header shows "offline" pill, activation disabled |
| MSAL token cache lost (unsigned build) | Identity marked "sign in again" |
